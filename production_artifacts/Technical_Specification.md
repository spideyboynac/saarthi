## 1. Executive Summary

**Nyaya-Dhwani** ("Voice of Justice") is a voice-first, multilingual, Dual-RAG Legal Literacy Conversational Agent designed to make complex legal rights and procedures understandable and accessible to all citizens, regardless of literacy level.

The system features:
- **Hybrid Routing**: Uses Cloud API (Claude) when internet connectivity is available, falling back seamlessly to an offline local LLM (Ollama `llama3.1:8b-instruct-q4_K_M`) when offline.
- **Short-TTL Call Session State**: In-memory caller state object per call (`call_session: { phone_hash, last_answer_text, last_answer_tier, call_active }`) to manage stateful interactions without expensive re-computation.
- **6-Action Control Map with RAG Bypass**: Strict routing rules for voice IVR and web UI controls, bypassing vector search re-retrieval for repeat, simplify, and follow-up actions.
- **Voice-First SPA Dashboard**: Single Page Application with massive 120px-high pictogram buttons and non-overlapping tooltips for seamless user interaction.

## 2. Core Architecture & Hybrid Routing

### 2.1 Online / Offline Hybrid Router
- **Primary Route**: Cloud API (Claude) when internet connectivity ping is available.
- **Fallback Route**: Local LLM via Ollama (`llama3.1:8b-instruct-q4_K_M`) running locally when offline.
- **Health Check & Latency Detection**: Automatic network monitoring to toggle between online (Claude) and offline (Ollama) LLM routes without dropping active calls or breaking session flow.

### 2.2 Short-TTL Session Memory Object
Each active call or user session maintains a short-TTL memory object (`call_session`):
```json
call_session: {
  "phone_hash": "string (SHA-256 anonymized caller identifier)",
  "last_answer_text": "string (most recent synthesized answer text)",
  "last_answer_tier": "SIMPLE | STANDARD | DETAILED",
  "call_active": boolean
}
```
- **TTL Lifecycle**: Retained in memory during active call / browser session and automatically purged after session termination or TTL expiration (15 minutes).

## 3. The 6-Action Control Map & RAG Bypass Rules

Both telephony (Twilio Voice IVR) and web/mobile SPA UI execute according to the following 6-action control matrix:

| Action | Name | Technical Pipeline & Logic | RAG Bypass Strategy |
|---|---|---|---|
| **Action 1 / 2** | **New Question / End Input** | Triggers speech capture / audio stream termination. Audio is transcribed via Deepgram STT, translated via IndicTrans2, and routed through **Dual-RAG pipeline** (Legal Knowledge RAG + Case Example RAG). Result is cross-encoder reranked (Top 5) and generated by LLM. | **RAG Executed**: Vector DB search across both legal statutes and case precedents. |
| **Action 3** | **Repeat** | Directly replays stored `last_answer_text` from `call_session`. Re-synthesizes audio or replays cached audio buffer. | **STRICT RAG Bypass**: Zero LLM generation and zero vector search. |
| **Action 4** | **Simplify** | Drops literacy tier (e.g., STANDARD -> SIMPLE). Passes `last_answer_text` from `call_session` directly to LLM with a narrow prompt to rewrite into simpler terms. | **STRICT RAG Bypass**: Bypasses vector re-retrieval; operates strictly on `last_answer_text`. |
| **Action 5** | **Follow-Ups** | Passes `last_answer_text` from `call_session` directly to LLM to suggest Socratic queries (2-3 follow-up questions). | **STRICT RAG Bypass**: Bypasses vector re-retrieval; generates queries from `last_answer_text`. |
| **Action 6** | **Stop** | Immediate barge-in / interrupt signal to stop active audio playback (Twilio `<Play>` stream or Web Audio API) mid-response instantly. | **N/A**: Immediate execution playback interruption. |

## 3.1 ZERO MOCK DATA POLICY ⛔ (v3.0 — ABSOLUTE ENFORCEMENT)

> ⚠️ **CRITICAL**: This policy supersedes all prior "NO MOCK DATA" language in v2.x. The previous builds contained fatal pipeline corruption caused by mock data bypasses. **ZERO MOCK DATA** is an absolute, non-negotiable constraint on every file in this codebase.

### What is Forbidden — Zero Exceptions

The following are **unconditionally forbidden** anywhere in the codebase, in any file, at any time:

1. **Hardcoded audio bytes or Base64 audio strings** used as input substitutes. No variable named `MOCK_AUDIO`, `TEST_AUDIO_B64`, `SAMPLE_AUDIO`, or any equivalent.
2. **Hardcoded question or answer text strings** used as input substitutes. No variable or constant containing a pre-written legal question (e.g., `"What are my rights regarding unpaid salary?"`) or a pre-written legal answer injected into the pipeline.
3. **Mock response functions**: `getMockResponse()`, `getFakeAudio()`, `mockSTTTranscription()`, `getFallbackAnswer()`, or any function whose purpose is to fabricate pipeline outputs without executing real services.
4. **Server-side dummy responses**: Any backend code path that returns a hardcoded JSON body or text string in place of a real LLM, RAG, STT, or TTS service call.
5. **Client-side fabrication**: Any frontend code that generates or injects a fake LLM answer into the UI when the backend is unreachable (outside of connection-error display).

### What is Permitted

- **UI skeleton / loading states**: Spinner, "Processing…" text, or blank placeholder cards while awaiting a real backend response — these are display states, not data fabrication.
- **Connection error messages**: Displaying `"Connection failed. Check that the backend is running."` when the WebSocket is unreachable — this is an error state, not a fabricated answer.
- **Unit test fixtures**: Isolated test files (e.g., `run_tests.py`, `test_*.py`) may use recorded audio bytes or fixed query strings **only within test scope**, never in production code paths.

### Enforcement Rule
Any code change that introduces mock data into a production code path is a blocking violation. The pipeline must either work end-to-end with real APIs or fail explicitly with a logged error.

## 3.2 ACTION 1 — Exact End-to-End Pipeline Definition

> This section defines the **complete, unambiguous data flow** for Action 1 (New Question) through Action 2 (Voice Input Over). Every step is mandatory. No step may be skipped or substituted with mock data.

### Step-by-Step Data Flow

```
━━━━━━━━━━━━━━━━━━━━ FRONTEND ━━━━━━━━━━━━━━━━━━━━

[1] User presses Action 1 (New Question)
    → navigator.mediaDevices.getUserMedia({ audio: true })
    → Acquire live MediaStream from hardware microphone
    → Create MediaRecorder from stream
    → Connect stream to AnalyserNode for live AudioVisualizer waveform
    → MediaRecorder.start() — begin capturing audio chunks

[2] User presses Action 2 (Voice Input Over)
    → MediaRecorder.stop()
    → Assemble all recorded Blob chunks into one Blob
    → FileReader.readAsDataURL(blob)
    → Base64 audio string produced (includes data-URI prefix)

[3] WebSocket Send
    → Target: ws://localhost:8080/ws/audio
    → Payload:
      {
        "action": "PROCESS_AUDIO",
        "audio_b64": "<base64_string_with_or_without_data_uri_prefix>",
        "phone_hash": "<session_identifier>"
      }

━━━━━━━━━━━━━━━━━━━━ BACKEND (/ws/audio) ━━━━━━━━━━━━━━━━━━━━

[4] WebSocket Receive & Decode
    → Strip data-URI prefix if present (e.g., "data:audio/webm;codecs=opus;base64,")
    → base64.b64decode() → raw audio bytes

[5] STT — Deepgram API (hackathon build)
    → POST https://api.deepgram.com/v1/listen?model=nova-2&detect_language=true
    → Headers: { "Authorization": "Token $DEEPGRAM_API_KEY", "Content-Type": "audio/webm" }
    → Body: raw audio bytes
    → Extract: results.channels[0].alternatives[0].transcript → transcribed_text
    → Production target: IndicASR / IndicWav2Vec

[6] Translation — IndicTrans2
    → If transcribed_text is in a native Indian language (auto-detected by Deepgram)
    → IndicTrans2 translates native_text → English query string
    → If already English, pass through unchanged

[7] Dual RAG Retrieval
    → Legal Knowledge RAG: bge-large-en-v1.5 embedding → top-20 statute/scheme passages
    → Case Example RAG: bge-large-en-v1.5 embedding → top-20 case precedent passages
    → MS-MARCO-MiniLM-L-6-v2 cross-encoder reranker over combined 40 candidates
    → Output: Top 5 highest-scoring passages with source citations

[8] LLM Generation — Claude API (online) / Ollama (offline fallback)
    → System prompt: grounded strictly in the Top 5 retrieved passages
    → Descriptive language only ("the law states X", never "you should X")
    → Output: English answer text, cited against retrieved sources
    → Literacy tier from call_session.last_answer_tier applied

[9] Translation — IndicTrans2
    → English answer text → native language of the caller
    → Legal glossary layer applied (corrects domain-specific term translation errors)
    → Output: native_language_answer_text

[10] TTS — ElevenLabs API
    → POST https://api.elevenlabs.io/v1/text-to-speech/{voice_id}
    → Model: eleven_multilingual_v2
    → Input: native_language_answer_text
    → Output: audio bytes → base64.b64encode() → audio_b64_response

[11] session_service.update_session() — store last_answer_text, last_answer_tier

[12] WebSocket Send (success path)
    → {
        "action": "AUDIO_RESPONSE",
        "audio_b64": "<base64_audio>",
        "text": "<native_language_answer_text>",
        "literacy_tier": "<SIMPLE|STANDARD|DETAILED>",
        "rag_executed": true,
        "llm_route": "<CLAUDE_CLOUD|OLLAMA_LOCAL>",
        "sources": ["<citation_1>", "<citation_2>", ...]
      }

━━━━━━━━━━━━━━━━━━━━ FRONTEND ━━━━━━━━━━━━━━━━━━━━

[13] Audio Playback
    → Receive audio_b64 → atob() → Uint8Array → AudioBuffer
    → Web Audio API: AudioContext.decodeAudioData() → AudioBufferSourceNode.start()
    → Display text answer in ResponseCard
    → Display source citations
```

## 3.3 TTS ERROR FALLBACK — Browser `SpeechSynthesis`

> This section defines mandatory behavior when ElevenLabs TTS is unavailable. Voice output **must never be silently dropped**.

### Backend Behavior on TTS Failure

When ElevenLabs returns a non-2xx status, times out, or returns empty audio bytes:

1. The backend **MUST NOT** send an `audio_b64` field in the response.
2. The backend **MUST** send the following distinct fallback message over the same WebSocket connection:

```json
{
  "action": "TTS_FALLBACK",
  "text": "<native_language_answer_text>",
  "literacy_tier": "<SIMPLE|STANDARD|DETAILED>",
  "rag_executed": true,
  "llm_route": "<CLAUDE_CLOUD|OLLAMA_LOCAL>",
  "sources": ["<citation_1>", "..."],
  "error": "TTS_UNAVAILABLE"
}
```

### Frontend Behavior on `TTS_FALLBACK`

Upon receiving a message with `"action": "TTS_FALLBACK"`, the frontend **MUST**:

1. Display the `text` field in the `ResponseCard` component.
2. Show a visible, non-blocking UI indicator: **🔊 Using device voice (ElevenLabs unavailable)**
3. Invoke the browser's native speech engine:
   ```javascript
   const utterance = new SpeechSynthesisUtterance(message.text);
   window.speechSynthesis.speak(utterance);
   ```
4. Allow Action 6 (Stop) to cancel the native utterance via `window.speechSynthesis.cancel()`.

### What is Forbidden in the Fallback

- Sending `"audio_b64": ""` (empty string) — silently unfreezes the UI without providing voice output and masks the failure.
- Displaying a generic "TTS Failed" error without reading the answer aloud.
- Swallowing the error silently.

## 4. UI/UX Constraints (Phase 2 Single Page Application)

### 4.1 Single Page Application Layout
- **Zero Deep Menus**: Voice-first dashboard displayed on a single, intuitive screen with zero multi-level menus or navigation transitions.
- **Massive Pictogram Buttons**:
  - Exactly 6 large action buttons, each **strictly 120px high**, arranged in a responsive touch-friendly grid.
  - High-contrast, intuitive vector pictograms (Microphone, Stop Recording/Send, Circular Replay Arrow, Lightbulb/Simplify, Socratic Question Mark, Hand Stop Sign).
- **Non-Overlapping Tooltips**:
  - Tooltips styled with explicit z-index isolation, boundary checking, and padding to guarantee tooltips **MUST NOT overlap** with adjacent buttons, neighboring tooltips, or UI panels.
- **Live Status Badges**:
  - Dynamic status indicator for Network/LLM Route (`ONLINE (Claude API)` vs `OFFLINE (Ollama)`).
  - Active Literacy Tier badge (`SIMPLE` / `STANDARD` / `DETAILED`).

### 4.2 Hardware Enforcements (carried forward from v2.1)

**NATIVE BROWSER MICROPHONE**
- **Action 1 (Ask New Question)** MUST trigger `navigator.mediaDevices.getUserMedia({ audio: true })` to acquire a real audio stream from the user's hardware microphone.
- A `MediaRecorder` instance MUST be created from the acquired stream to capture audio chunks.
- The `AudioVisualizer` component MUST connect to the live `MediaStream` via `AnalyserNode` for real waveform data — no fake CSS bar animations.

**AUDIO ENCODING & WEBSOCKET TRANSPORT**
- **Action 2 (Voice Input Over)** MUST:
  1. Call `mediaRecorder.stop()` to finalize the recording.
  2. Assemble all recorded chunks into a single `Blob`.
  3. Convert the `Blob` to a **Base64 string** using `FileReader.readAsDataURL()`.
  4. Send the audio over a **WebSocket** connection in this **exact JSON format**:
    ```json
    {"action": "PROCESS_AUDIO", "audio_b64": "<base64_string>"}
    ```
  5. The WebSocket URL MUST be `ws://localhost:8080/ws/audio`.

**BACKEND AUDIO DECODING**
- The FastAPI backend MUST expose a **WebSocket endpoint** at `/ws/audio`.
- Upon receiving the `{"action": "PROCESS_AUDIO", "audio_b64": "..."}` JSON message, the backend MUST execute the full pipeline defined in §3.2 — no short-circuits permitted.

## 7. Known Limitations (stated honestly)

- Single-context-window RAG struggles with reasoning across multiple statutes simultaneously.
- ElevenLabs TTS requires internet — SpeechSynthesis fallback (§3.3) mitigates for web UI; Twilio phone path has no voice fallback when fully offline.
- Corpus scoped narrow for demo; full coverage is future work.
- Twilio call latency stacks across 4+ processing hops — hold message is a mitigation, not a fix.
- IndicTrans2 translation layer is present in the architecture but operates as a pass-through in the hackathon build; full integration is the production milestone.
